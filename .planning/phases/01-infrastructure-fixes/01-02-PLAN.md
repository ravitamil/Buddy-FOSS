  <name>Task 1: Create centralized query key factory</name>
  <files>src/lib/query-keys.ts</files>
  <action>
Create `src/lib/query-keys.ts` with array-based query key families for all 10 domains. Per locked decision: domain + operation granularity, single central file, structure enables prefix invalidation.

The factory must follow this pattern for each domain:

```typescript
export const queryKeys = {
  transactions: {
    all: ['transactions'] as const,
    lists: () => [...queryKeys.transactions.all, 'list'] as const,
    list: (uid: string) => [...queryKeys.transactions.lists(), uid] as const,
    details: () => [...queryKeys.transactions.all, 'detail'] as const,
    detail: (uid: string, id: string) => [...queryKeys.transactions.details(), uid, id] as const,
  },
  // ... same pattern for other domains
} as const;
```

All 10 domains (per locked decision): transactions, budgets, groups, loans, investments, savings, subscriptions, categories, wallets, analytics.

Special cases:

- `investments` needs a nested `categories` sub-family (the codebase has `['investment_categories']` as a separate key)
- `analytics` needs `summary` and `trends` (with range parameter) instead of list/detail
- `categories` only needs `all`, `lists`, `list` (no detail -- categories don't have individual detail views)

Key structure must ensure `queryClient.invalidateQueries({ queryKey: ['transactions'] })` matches all transaction queries. This means UID goes after the operation discriminator: `['transactions', 'list', uid]` not `['transactions', uid, 'list']`.

Follow the exact structure from the RESEARCH.md Code Example 1 which has the complete 10-domain implementation.
</action>
